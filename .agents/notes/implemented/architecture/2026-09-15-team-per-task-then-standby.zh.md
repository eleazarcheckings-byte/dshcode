# Agent Note: 每任务一支团队，然后待命

Status: implemented

[English](2026-09-15-team-per-task-then-standby.md) | 中文

## Problem

多任务模式此前写着"在独立专家之间协调实质性工作，同时自己也取得有用的进展"，并以"把琐碎读取、直接编辑和紧密依赖的工作留在主线程"收尾。对一个有能力的模型来说，这等于允许它独自完成大部分任务：任何任务都能被论证为"紧密依赖"，而一个兼任构建者的主导者，不过是披着开关名字的单线程。策略也没有说明结果落地之后会发生什么，因此一个完成了一项任务的主导者可以顺理成章地直接滚入它自认为的下一项——没有人要求的工作，没有提示作为锚点就被派发出去。

izzy 在 2026-09-15 明确了预期的形态：多任务模式指定一支团队来解决任务，然后进入待命，等下一项任务的提示到来时再指定另一支团队。组队者组建的是代理团队，绝不是单个代理。

## Decision

ON 策略现在在第一句和最后一句写明这一形态。

**每任务一支团队，并设下限。** 对用户交来的每一项任务，主导者组建一支团队并把任务交给它——绝不是单个代理。一支团队至少由两位写入范围互不重叠的专家外加末尾的独立评审者组成。这条下限是"团队"一词有意义的前提：没有它，一个子代理加主导者就能满足规则的字面。规模仍按任务缩放，最小的自洽团队即为正确的团队——防碎片化的护栏得以保留，但它现在只从上方约束团队规模，绝不会把团队压缩成一只手。

**主导者组队；团队解题。** 允许主导者把工作留在主线程的那句话已被删除。留在主导者自己手中的，是锁定上下文的读取——一份任务书所需的材料——因为组建团队需要先了解任务。解决任务属于团队。

**然后待命。** 团队经验证的结果交付之后，主导者汇报并等待下一条提示。它不会自行开始下一项任务；下一条提示会得到一支新组建的团队。证明闸门决策中的独立评审规则不变，位于两者之间：构建，由未参与构建者评审，交付，待命。

测试固定的是策略的措辞而非精神：团队下限（"at least two"）、"in the main thread" 的缺席、待命（"stand by"、"next prompt"、"do not start the next task"），以及 OFF 覆盖不携带其中任何内容——OFF 仍是用户的单一直线线程。

## Alternatives considered

- **在代码中强制下限——拒绝派发少于两位专家的轮次**——被否决：orchestrate 包只贡献提示文本，README 已经写明 ON 与 OFF 是指引而非强制。真正重要的强制在证明闸门，它不关心结果由多少只手构建，只关心是否有独立者评判过。统计委派次数还会惩罚那种任务确实只有一个切片加评审者的诚实情形。
- **保留"紧密依赖的工作留在主线程"作为例外**——被否决：正是这一从句吞掉了规则。让团队中的一位专家端到端拥有一个紧耦合切片，结果相同，而主导者不必沦为工人。
- **只把待命规则写进 harness 附录**——被否决：附录通过 `AGENTS.md` 到达主导者，但 `orchestrate:policy` 段落才是开关真正移动的文本，而设为 OFF 的会话绝不能携带这条规则。两份副本都存在；策略是开关所管辖、测试所读取的那一份。
- **把团队下限设为三（两位专家加一位研究者）**——被否决：它会把研究之手强加给不需要研究的任务，这正是护栏要防止的碎片化。

## Consequences

新会话折叠为未激活；上面的 ON 形态是开关打开之后才生效的内容（[Saturn 产品法默认值](../feature/2026-09-15-saturn-product-law-defaults.zh.md)）。ON 会话中的每一项任务现在至少花费两个专家上下文加一个评审者上下文，包括那些单只手本可以更快完成的小任务。这是有意的取舍：产品的主张是每条提示都得到经验证的团队结果，而下限的代价以 token 支付，而非以信任支付。待命意味着会话绝不会在两条提示之间自行推进工作——想要持续推进的操作者以一条提示提出要求，并为它得到一支团队。

harness 附录的质量护栏已重述为一致的表述：最小的自洽团队，绝不是单只手。saturnai.tools 上协调者姿态文本的引擎副本携带同一段落，由拥有引擎的进程更新。

证据：`packages/saturn/orchestrate/tests/policy.spec.ts`——`team per task, then stand by` 的四个用例在旧策略文本下失败、在本文本下通过，经由 `resolveConfig()` 与组装后的提示两条路径。
