# Agent Note: Browser control parity — refs, interaction, reads, tabs, auto-fetch

Status: implemented

English | [中文](2026-09-16-browser-control.zh.md)

## Problem

`@deepseek-ai/dsh-tool-browser` could open a page and read its accessibility tree, but not act on it: no click, type, fill, press, hover, or scroll, no way to address one element deterministically, no console/network visibility, no second tab, and no screenshot bytes. A fresh Saturn install also has no Chromium cached, so the first navigate failed on a clean PC with only an install-guidance error, never proceeding on its own. The Mars gap-plan review (`mars-gap-plan.json`, correction 2) additionally corrected the original architect plan: `browser_snapshot` already returns a Playwright ARIA accessibility tree — the `read_page` equivalent — so the fix is to extend it additively with stable refs, not build a parallel tool.

## Decision

Extend `browser_snapshot` to capture the ARIA tree with Playwright's `ariaSnapshot({ mode: 'ai' })`, which embeds `[ref=eN]` handles resolvable through Playwright's own `aria-ref=` locator selector engine — confirmed empirically (a probe script against real Chromium) to stay identical across two snapshot calls on an unchanged page, and to resolve correctly through `page.locator('aria-ref=e3')` even after later snapshot calls. This meant no custom shadow-DOM ref-tracking layer was needed: `resolveElementSelector({ ref, selector })` in `session.ts` maps a `ref` to `aria-ref=<ref>` and passes a `selector` straight through, and every interaction tool accepts exactly one of the two.

New tools: `browser_click`, `browser_hover`, `browser_fill`, `browser_type` (with `submit`), `browser_press` (targeted or page-level), `browser_scroll` (element-into-view or directional viewport), `browser_page_text`, `browser_console`, `browser_network`, `browser_tabs` (list/new/select/close), `browser_screenshot`. `BrowserSession` (`session.ts`) was restructured from a single `tab` field to a `ManagedTab[]` list with an `activeId`, preserving the exact launch/dispose race contract the original single-tab implementation was tested against (a concurrent `dispose()` must close the just-launched process exactly once, never zero or twice) — this required NOT racing `process.newTab()` itself against the caller's `AbortSignal` (only the launch and the subsequent navigate are raced), matching the original `ensureTab`'s behavior exactly, or an existing abort-race test flips from one close to zero.

Console and network capture attach `page.on('console'|'request'|'response', …)` listeners once per tab, at creation, into a per-tab ring buffer capped by the deployment's `consoleLimit`/`networkLimit` (oldest evicted first); a network record's `status` fills in asynchronously via the `response` event, keyed off the `Request` object through a `WeakMap` rather than the URL (a URL can repeat across requests).

**Chromium auto-fetch.** `downloader.ts` shells out to `playwright-core`'s own bundled CLI (`playwright-core/cli.js install chromium`, located by joining `dirname(require.resolve('playwright-core/package.json'))` with `cli.js` — that subpath is the package's declared `bin` target but not an `exports` entry, so it is reached via the resolved package directory rather than package-export resolution) rather than a bespoke Chrome-for-Testing downloader: it always fetches the exact build `playwright-core` at this version expects, lands in the same `ms-playwright` cache `pnpm exec playwright install chromium` would use (so a later manual install, or another package's own Playwright, sees the same cache and skips re-downloading), and needed no new dependency. `playwright.ts` detects a missing-executable launch failure by matching Playwright's own `Executable doesn't exist` error text, attempts the auto-fetch only when neither `executablePath` nor `channel` is pinned and `autoDownload` is not disabled, then retries the launch once; a failed download's error (minted in `downloader.ts`) already names the manual command, so `launchPlaywright` does not re-wrap it. Progress lines are forwarded to a caller-supplied `onDownloadProgress` callback; `index.ts` wires that to `process.stderr`, documented in the README as the current mechanism given `dsh-tools` has no dedicated tool-progress channel — a real gap, not papered over.

**URL policy.** `urls.ts` denies `169.254.0.0/16` (IPv4, including hex/octal/decimal-integer spellings and the range embedded in an IPv4-mapped IPv6 literal — the WHATWG `URL` parser already canonicalizes the former to dotted-decimal before this check runs) and IPv6 `fe80::/10`, while keeping loopback and RFC1918 private ranges reachable, per the mandate's explicit instruction to preserve local-dev-server verification.

**Attachments seam, deliberately not wired.** `browser_screenshot` returns only `{ screenshotPath, mediaType, bytes }`, not an in-band `ImageBlock` through the attachments seam `read_image` uses. `@deepseek-ai/dsh-attachment` is not in this package's `node_modules` (confirmed: `require.resolve` fails from this package, though the workspace package is already built in the pnpm store) and this package's `package.json` does not declare it. Repo rule: a needed dependency not already resolvable must not be silently added and assumed installed — report it and stop that piece. Recorded as a Known Limitation and an integration need rather than worked around with an untyped/duck-typed cast through an unimported branded type.

## Alternatives considered

- **A parallel `read_page` tool** — the original architect plan's framing. Rejected per the Mars correction: `browser_snapshot` already is the accessibility-tree read; a second tool with overlapping output would fragment the model-facing surface DSH's own conventions warn against.
- **A custom ref-tracking layer (assign IDs to DOM nodes via an injected script)** — unnecessary once Playwright's own `mode: 'ai'` snapshot and `aria-ref=` locator engine were confirmed to do exactly this, and matches the same mechanism Playwright's own MCP server uses.
- **A raw Chrome-for-Testing JSON-endpoint downloader** — the mandate allowed it as a fallback, but `playwright-core`'s bundled installer is already the mechanism that guarantees the exact expected build and reuses the standard cache location; reimplementing it would only risk drifting from whatever `playwright-core`'s own version pins.
- **Casting an untyped image content block into the render output to satisfy the literal "returns image content" ask** — would pass `tsc` today but ship a value whose `attachmentId` is not a validly-branded `AttachmentId`, silently correct only by accident of the brand being erased at runtime; rejected in favor of an honest, reported dependency gap.

## Consequences

The `standard`/`cordis` preset's browser surface goes from navigate+read to real control: a model can locate an element once (via `browser_snapshot`'s refs) and act on it repeatedly across click/type/fill/press/hover/scroll calls without re-snapshotting between each one, as long as the page does not change. `browser_tabs` lets one agent hold two pages open (e.g., compare a before/after) within the same shared-tab-per-preset model the original package already had. A clean install no longer dead-ends on the first navigate when no Chromium is cached — it downloads once, visibly, and proceeds. `browser_screenshot`'s bytes stay file-path-only until a follow-up adds `@deepseek-ai/dsh-attachment` to this package (peer + dev dependency, plus a `tsconfig.json` reference) and a `pnpm install` links it — named explicitly rather than assumed.
