# Agent Note：远程通知环上的回放窗口

Status: implemented

[English](2026-09-15-remote-access-replay.md) | 中文

## 问题

远程访问通过一条 Server-Sent Events 流通知已配对设备。对于醒着并保持着套接字的设备，流是正确的形状；而对于这项功能真正服务的那台设备，它是错误的形状。手机会挂起应用；iOS 与 Android 都会按自己的节奏回收后台套接字；WebView 会重新加载。套接字消失期间发布的帧，恰恰是最要紧的那些——仍在等待的审批、刚刚落定的判定。`Last-Event-ID` 能够找回它们，但前提是客户端还能重新连上一条流，而且它以无界推送的形式到达，而不是一个后台任务可以发问、读取、然后结束的答复。

## 决策

在流的旁边增加一条只读路由：`GET /saturn/remote/events/replay?after=<id>&limit=<1..200>`，回答 `{ events, newest, truncated }`；当环形缓冲区已经淘汰了该游标索要的内容时，再加上 `"gap": true`。

它复用，而非另起炉灶。帧取自 `Last-Event-ID` 已在使用的同一个有界环，序列化为流所承载的同一批对象，守在同一道设备令牌的门后（Bearer 请求头或设备会话 Cookie），以及同样的浏览器栅栏之后。没有新增存储，也不存在第二条通知路径——一个发布者，一个环，两种读法。

三条性质构成了这个形状的全部要点。它**会结束**：设置 `Content-Length`，没有心跳，后台任务可以等待它完成。它**严格**：`after` 必须是从零起的整数，`limit` 必须落在 1–200 之间，否则一律 400——设备的游标要么是主机写下的数字，要么就是一个错误，而把错误夹取到区间内只会让它永远不可见。它**对丢失诚实**：`truncated` 表示窗口小于积压，`gap` 表示积压本身已经不在。若没有 `gap`，一台睡过 100 帧的设备会收到 64 帧，却无从得知自己丢掉了 36 帧。

## 备选方案

**交给 `Last-Event-ID` 就好。** 它需要一条流，而流正是手机保不住的那样东西。它也无法说出“你错过了一些我已不再持有的帧”，因为推送没有地方安放这句话。

**把事件持久化，让回放拥有真正的历史。** 持久日志意味着一个文件、一套轮转策略、一份 schema，以及一个新的、会把通知正文为一台已被吊销的设备留在磁盘上的东西。环存在于内存中，随进程一同消亡，其容量正对应回放真正承担的工作：让睡着的手机追上进度，而不是审计一整周。改为记入已知限制。

**把越界的 `limit` 夹取到区间内，而不是拒绝它。** 请求 `limit=0` 的设备相信着某件并不成立的事；用 100 帧去回答它，只会让两端的缺陷永远被掩盖。

**用时间戳做游标。** id 本就单调，本就在线路上，也本就是流让设备记住的东西。一个环配两套游标词汇，正是它们开始漂移的方式。

## 影响

`EventBus` 增加了一个纯读取方法 `replay(after, limit)`，`attach` 原封未动；路由是代理中那段已完成鉴权的远程分支里的一个判断，置于精确匹配 `/events` 之前，使流保留自己的路径。`gap` 仅在为真时出现——从未见过这个键的设备，本就不曾缺少什么。

组合测试如今在这条路由真正可达的地方证明它：经由固定证书的 TLS 套接字，在一次真实的 `approval/request` waterfall 之后，验证 `after=0` 逐字节返回流已投递的帧，`after=<newest>` 返回空数组并回传游标，`limit=1` 返回一帧且 `truncated: true`，七种畸形窗口各自被 400 拒绝，未配对的请求被 401 拒绝。淘汰场景需要 65 帧才能触及，因此环自身的窗口由旁边的单元测试覆盖——包括“连续的游标并非 gap”这一边界。
