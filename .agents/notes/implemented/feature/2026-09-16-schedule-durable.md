# Agent Note: Restart-durable, workspace-bound scheduled tasks

Status: implemented

English | [中文](2026-09-16-schedule-durable.zh.md)

## Problem

The only scheduling primitive in the harness was `@deepseek-ai/dsh-schedule`: a reminder folded from one Session's own event log, delivered back into that Session as a follow-up message. Its delivery mode is explicitly `session-local` — a cold or closed Session leaves a due reminder overdue until a future live root Agent resumes it, and a fixed-rate rule is anchored to the Session that created it. SaturnBot has its own durable cycle scheduler, but it is a standing business-automation loop with a planner, fixed roles, and channel adapters — not a general-purpose "run this on a schedule" primitive, and reusing it for an arbitrary cron or one-off task would mean adopting all of that machinery for none of its purpose. Nothing in the harness let a task survive a harness restart, bind to a workspace rather than a Session, or use calendar-style cron syntax, which is the gap against Claude Code's own scheduled routines.

## Decision

`@deepseek-ai/dsh-schedule-durable` is a new package, composing beside `dsh-schedule` rather than replacing it. Every durable field — id, name, prompt, workspace, the cron-or-once rule, status, `nextFireAt`, `lastFiredAt` — is persisted through the `dsh-storage-domain` seam (a `schedule_durable` domain with one `tasks` table), never through the Session log; the package declares no `SessionEventMap` member. Cron parsing is a small in-tree 5-field parser (minute hour day-of-month month day-of-week, UTC), not a new dependency: it splits into value-set fields and searches minute-granularity candidates forward from the decision instant, fast-forwarding whole months, days, and hours that cannot match so an unreachable rule (day-of-month 31 restricted to a month set with no 31st, for example) still terminates within a bounded ten-year horizon rather than looping forever. The reconciliation decision — `reconcileTask(task, nowMs)` — is a pure function of an explicit instant: no internal `Date.now()` call, so every test supplies its own clock and the exactly-once-catch-up behavior is asserted deterministically rather than raced against a real timer. Catch-up is exactly-once by construction, not by a counter: a due task's next occurrence is always computed strictly after the reconciliation instant, never by walking forward from the missed occurrence, so however many occurrences were missed, one pass fires the task once and re-arms it at the correct future target; the identical rule governs `resume`, so a resumed task never replays the interval it was paused for. Firing a task is split from acting on it: the package resolves a `TaskDispatcher` duck-typed from `ctx.get('scheduleDurableDispatcher')`, exactly like the model-router seam documented in `@saturnai/dsh-model-router`, and without one configured a firing is recorded through `ctx.logger` and reported as `{ kind: 'dispatched', detail: 'no scheduleDurableDispatcher configured; no action was taken' }` rather than silently dropped or silently pretending an action occurred.

## Alternatives considered

**Starting a fresh agent session directly from this package on every firing.** The originating mandate asked for dispatch to start a fresh agent session in the task's workspace through the existing agent/session API. Investigation of `@deepseek-ai/dsh-subagent` found that its `ctx.subagents.start()` seam requires a live spawning Agent: its own documentation states that in-process providers derive workspace, lineage, and delegation depth from the spawning Agent's durable session state, which a headless restart-time reconciliation pass does not have — there is no live Agent to spawn from when the harness has just booted with no open session. Building a cold-start-safe top-level session bootstrap was out of this package's exclusive write scope (`packages/schedule/schedule-durable/**` only) and would touch the Agent/Session stack this session's rules forbid. The dispatcher seam is the honest boundary: this package proves exactly when a task is due and fires it exactly once; what a firing does is a deployment-level integration decision, documented as a Known Limitation rather than papered over with an agent-spawn call that would fail every time it actually ran without a parent Agent.

**Folding this into `dsh-schedule`'s own Session-log fold.** Rejected because the two delivery models are incompatible at the persistence layer: `dsh-schedule` is deliberately Session-log-authoritative (strict replay, fork-aware `ownEvents()` cuts, no external channel), while a workspace-bound task must outlive any one Session's log entirely. Composing beside it, not extending it, keeps both contracts clean and matches the mandate's explicit fence against editing the session-scoped package.

**Borrowing SaturnBot's scheduler.** Rejected per the mandate itself and confirmed by inspection: SaturnBot's `scheduler.ts`/`engine.ts` are wired to its own planner/specialist model roles and channel adapters (`BotOrchestrator`, `BotAgent`, `propose`/`plan`), not a general-purpose fire-a-task primitive; adopting it for an arbitrary cron task would mean adopting a business-automation loop for no reason.

## Consequences

A deployment gets restart-durable scheduling today with zero side effects until it explicitly wires a dispatcher: mounting the plugin alone is safe (no outbound sends, no session mutation, no agent spawn), matching the originating mandate's scope fence that this package schedules and does not act. Wiring a real dispatcher — most usefully one that starts an agent session — is deferred to a future integration that first needs a cold-start-safe session bootstrap this package does not build. No bundle row or preset row is wired yet; both are named in this package's integration needs for the orchestrator to add (a `- id: schedule-durable` row in `packages/bundle/base/cordis.patch.yml`, and the corresponding `tsconfig.base.json` path plus a root tsconfig reference), since this package's exclusive scope forbids editing any of those files itself.

## Verification

`node_modules/.bin/vitest run packages/schedule/schedule-durable` — 4 files, 30 tests, all green: cron parsing rejects malformed field counts, out-of-bound terms, reversed ranges, and invalid steps, and folds day-of-week 7 onto 0; next-fire search covers a plain wildcard, an explicit minute/hour target, rolling to the next day, a step value, a day-of-week list, a month-end skip (day-of-month 31 against a 30-day month), the day-of-month/day-of-week OR-join, February 29 landing only on a leap year, and an unreachable rule (February 30) reporting `undefined` rather than looping; the store round-trips id, cron, next-fire, and workspace across two independent `Context`s over the same JSON-backend root (a simulated restart), deletes durably with an idempotent second delete, and fails loud with `invalid-record` when a hand-crafted on-disk record carries an out-of-vocabulary `status`; `reconcileTask` proves exactly-once catch-up after two missed `*/10` occurrences (firing once and landing on the next `*/10` slot strictly after the decision instant, not the missed ones), one-shot completion, and paused suppression even with a stale past `nextFireAt`; `resumeNextFireAt` proves the cron recompute, the still-future one-shot pass-through, and the lapsed one-shot catch-up-on-next-pass cases; `ScheduleDurableRuntime.reconcileAll` proves the same exactly-once behavior end to end against a real storage-domain-backed store with an injected dispatcher, and separately proves the default recording dispatcher engages when none is configured; the plugin composition test proves the Loader-safe function-plugin export shape (no default export, `unwrapExports` round-trip), registers and executes all five tools against a real `ToolRuntime` with no live Agent required, rejects a non-absolute workspace and a doubled-or-missing cron/at selector with their stable codes, and proves restart catch-up fires automatically on mount by creating a near-future one-shot task, letting it lapse, tearing down the Context, and reopening a fresh one over the same root. `node_modules/.bin/tsc -p packages/schedule/schedule-durable/tsconfig.json --noEmit` exits clean.
