# Agent Note: the Gates are a data policy on the tool waterfall, not a branch per tool

Status: implemented

English | [中文](2026-09-16-saturn-gates.zh.md)

## Problem

The harness had no Gate. The permission model is two global knobs — a sandbox file mode crossed with an approval policy — and its shipped preset table has exactly three rows, of which the only one with full file access (`danger-full-access`) also sets approval to `never`. Nothing anywhere inspected a shell command's text or an MCP tool's name for the classes of act that should stop for a human: a force push, a production deploy, a credential read, a paid generation call, a message to a real person, an `rm -rf` outside the workspace. The one place a money Gate did exist — `packages/saturn/tool-media`'s spend approval — shares that same global knob, so under the operator's own `defaultPreset: danger-full-access` it auto-rejected every model-initiated call rather than asking him. The choice on offer was therefore "full capability with no Gates" or "Gates that always say no", and the operator's standing law is that credentials, money, public acts and irreversible acts always return to him while everything else runs.

## Decision

Ship `@saturnai/dsh-gates`: one `tools/pre-execute` listener over a policy that is DATA. Six consequence classes (credentials, spend, publish, outbound, identity, destructive), two rule shapes — an MCP rule matching a tool NAME because an MCP tool's name already states its effect, and a shell rule additionally matching a case-insensitive regular expression against the command text, scoped to the tools that actually run a command line and to the argument fields that hold one. The shipped rules name the servers the operator actually mounts (telegram-hive, shop-ops, gemini-media, saturn-browser, saturndesign, verified against his `.claude.json` roster of eleven), each paired with a `mcp__*__…` wildcard for the same effect on an unknown server. Four rules deny rather than ask — fork bomb, root or home wipe, disk format, raw block-device write — because no in-session approval should be able to buy them; everything else asks. A deployment appends rules, drops one by id, or replaces the set; a policy that cannot compile fails the plugin load rather than gating nothing.

Three composition decisions carry the design. **The plugin never calls `ctx.approval` itself**: it returns `{ kind: 'ask' }` and the tool registry resolves it, which is what keeps one call to one question and puts the ask/decision pair in the session's own audit log. **A claimed call is answered without delegating** (an unclaimed one always delegates), so mounting gates ahead of the Claude Code hook bridge means the Gate's classes are decided once. **A shell call already carrying a `sandbox_permissions` escalation is delegated even when an `ask` rule claims it**, because `tool-bash` resolves that escalation through the same approval seam inside its own body — abstaining is what keeps a Gate-class escalating call at exactly one question instead of two, and nothing runs unapproved either way since a refused, unanswerable, or agent-less escalation throws before the command runs. A `deny` class is decided before that check, so an escalation request can never buy a pass. Review tightened that abstention twice more: the mode must be one the sandbox family can actually be escalated to (`escalationModes`), because a request naming anything else is refused by that family's own widening check without a human seeing it, and two invented arguments would otherwise silence any `ask` rule; and the abstention is logged with its class and rule id, because it is the one path where the Gate claims a call and puts nothing of its own in front of the human.

The plugin also reads the effective approval policy before asking. Under `never`, an ask is answered `rejected` before any answerer sees it, so the model would report a refusal the user never made; instead the call denies with a reason that names the fix — switch `permission.defaultPreset` to `full-access-gated`. Tests first: the two suites landed RED in `a01573c710` (103 cases, the package's source absent), then the implementation landed without editing either spec file.

## Alternatives considered

- **Compose the dormant `@deepseek-ai/dsh-hooks-claude-code` bridge against the operator's existing `gate-guard.js` and call it done.** Rejected as the whole answer, kept as a complement: the bridge spawns a process per hook per call, its matchers are written against Claude Code's tool names rather than the harness's, and a policy that lives in a personal settings file outside the repository cannot be tested by the repository. The bridge still earns its place for everything bespoke; the Gate classes are native, typed, and covered.
- **Call `ctx.approval.request()` from inside the gate.** Rejected: the registry already resolves an `ask` through that seam with the call's id, signal, and session audit attached. Asking directly would duplicate the audit pair and, on an escalating bash call, put two questions in front of the user for one action.
- **Deny a Gate-class call that carries a sandbox escalation.** Considered as the simple way to guarantee one question, and rejected: it guarantees ZERO questions and teaches the model to retry without the escalation, which is worse behaviour for the same command. Abstaining keeps the human decision and the count. Review re-opened this, on the sound observation that the single prompt the human sees is the sandbox's — `escalate sandbox to <mode>: <the model's own justification>` — and never names the class, the rule id, or the rule's sentence, so the consent is real but less informed than on every other path. It stayed rejected for a mechanical reason as much as a design one: the committed RED specs pin that call at one prompt, not an error, with the command running, and a RED spec is not editable after the fact. What the round changed instead is everything that could be changed without it — an invented mode no longer suppresses the Gate, the abstention is on the record in the log, the asymmetry is a Known Limitation in both READMEs with its remedy (`deferToSandboxEscalation: false`) named, and a spec now pins the exact prompt text so the documented behaviour cannot drift silently. Closing the gap without paying a second prompt needs `tool-bash` to carry a caller-supplied reason into its own approval request; that is a change in a package this cell does not own.
- **Let `allow` exempt a tool from every rule.** How it shipped, and reverted in review. The exemption reads as an ask-level convenience, so a deployment adding `allow: ['bash']` to quiet noisy prompts would have unknowingly disarmed the fork-bomb, root-wipe, disk-format and raw-block-device denials. The exemption is now applied per rule and skips only `ask` rules; the four denies stay armed for an exempt tool.
- **Hardcode the classes as branches per tool.** Rejected by the repository's own rule against unsupported hardcoded tunables, and by the operational fact that mounting a new MCP server is a policy event: a branch would need a code change and a rebuild where a rule needs a config line.
- **Gate the file-mutation tools too.** Rejected: full file access is the point. The operator asked for a session that can write anything while money, credentials and public acts still stop.

## Consequences

A session can run with full file and shell access and still return to the human on the acts that matter, with a sentence naming the class, the rule, and what happens now. The cost is strictly per stopped call: no system-prompt section, no tool schema, nothing in the prompt prefix, so an unclaimed call is untouched and the KV cache is never invalidated by the policy. Four gaps are documented rather than hidden in the package README: a regular expression reads what a command says and not what it does, the harness still has no network egress control of any kind, a Gate-class tool on a server nobody listed passes through until a rule names it, and a Gate-class shell call carrying its own sandbox escalation is approved through the sandbox's question rather than the Gate's — informed-consent degradation on one path, not a bypass, with a config remedy and an upstream fix both named. The integration this cell does not own is named in its report: a `full-access-gated` preset row, the bundle row that mounts this plugin ahead of the hook bridge, and the `tsconfig` registration — without the preset switch every Gate-class call denies instead of asking, which is the one outcome this package can detect and explain but cannot fix.
