# Agent Note: A Claude Code hooks.json matches DSH tool names, not just Claude Code's own

Status: implemented

English | [中文](2026-09-16-hook-bridge-fidelity.zh.md)

## Problem

`dsh-hooks-claude-code` ran an unmodified Claude Code `hooks.json` faithfully in shape — matcher parsing, command substitution, decision mapping — but silently against the wrong vocabulary. Claude Code's own hooks (izzy's `gate-guard.js`, wired with matcher `Bash|PowerShell`, and the MCP companion matched by tool name) are written against Claude Code's tool names. This harness's own tool inventory (catalogued in `INV-harness-tools.json`) names the same capabilities differently: `bash`, `pwsh`, `edit`, `write`, `str_replace_editor`, `read`, `read_image`, `glob`, `grep`, `web_fetch`, `web_search`. A `PreToolUse` matcher group evaluated its pattern against `exec.name` directly (`matchesMatcher(group.matcher, exec.name, 'claude-code')`), so `Bash|PowerShell` never selected a `bash` or `pwsh` call, and `Edit|Write|MultiEdit` never selected `edit`, `str_replace_editor`, or `write`. A hook wired for exactly this purpose — Gate-class command detection — never fired. The synthesised `PreToolUse`/`PostToolUse` payload compounded it: `tool_name` was `exec.name` verbatim, so even a hook a bridge developer matched with a DSH-native pattern would read `tool_name: "bash"` where the reference tool always reports `"Bash"`.

Separately, config parsing iterated only its own `CLAUDE_EVENTS` allowlist (`for (const event of CLAUDE_EVENTS)`), so a config key outside it — `ConfigChange`, `PreCompact`, `SessionEnd`, or any of Claude Code's other unimplemented events — was never even looked at. That is correct containment (an unsupported event cannot register or invalidate anything), but it was also silent: a maintainer wiring a `ConfigChange` hook, expecting the documented "unsupported events are ignored" behavior, had no signal at load time that anything was skipped.

## Decision

`config.ts` gains a `toolAliases: Record<string, string[]>` table (`DEFAULT_TOOL_ALIASES`) mapping each Claude Code tool name to the DSH tool names it aliases, precedence-ordered by table key when more than one Claude name covers the same DSH tool (`str_replace_editor` under `Edit`, `MultiEdit`, and `NotebookEdit` — `Edit` wins by table order). `reverseToolAliases` builds the DSH-name → Claude-names index once at plugin load; `toolMatchCandidates(dshName, reverse)` returns the raw DSH name plus every Claude name aliasing it (`['bash', 'Bash']`), and the bridge's `PreToolUse`/`PostToolUse` listeners now match a group against ANY of those candidates (`matchCandidates.some(candidate => matchesMatcher(...))`) instead of the raw name alone — so a matcher written either way, `Bash|PowerShell` or `bash|pwsh`, fires. `claudeToolName(dshName, reverse)` picks the table-order-first Claude name for the synthesised payload's `tool_name`, falling back to the raw DSH name for a tool nothing aliases (`terminal_open`, an `mcp__*__*` tool). No field inside `tool_input` is ever renamed — it is always `exec.arguments` unchanged. For a `bash`/`pwsh`/`write`/`edit` call specifically, that needed no renaming to begin with: those DSH tools already name their argument `command` (`bash`/`pwsh`) or `file_path`/`content`/`old_string`/`new_string` (`write`/`edit`) — the same names Claude Code's own tool schemas use — because those DSH packages were themselves modeled on the reference tool contract. That field-compatibility is specific to those four tools and does **not** extend to `str_replace_editor` (aliased under `Edit`/`MultiEdit`/`NotebookEdit`, but its own fields are `command`/`path`/`file_text`/`insert_line`/`new_str`/`old_str`) or `read_image` (aliased under `Read`, with its own field shape) — a hook reading `tool_input.file_path` for either finds it absent; see the README's Known Limitations. `toolAliases` is a plugin config field; a configured entry REPLACES the default of the same Claude name (so a user overriding `Bash` does not lose `PowerShell`, `Edit`, …), and `validateToolAliases` rejects a malformed value (non-object, or a key whose value is not a non-empty array of non-empty strings) at load, naming the offending key.

`parseClaudeCodeConfig` now iterates the config's OWN keys (`Object.keys(hooksMap)`) instead of the supported-events allowlist, and a key outside `CLAUDE_EVENTS` is pushed to `skipped` with `{ event, type: 'event', reason: 'unsupported event' }` instead of being silently dropped before the loop even reaches it. The bridge's existing skip-warning loop (already used for a non-command hook type) branches on `reason` to log a distinct message naming the event. This is containment with a signal, not a behavior change: the event still cannot register or invalidate anything, and an invalid matcher inside an unsupported event's groups is still never evaluated (a pre-existing `config.spec.ts` case this note's change does not regress — verified directly).

## Alternatives considered

**Deep-merge a configured `toolAliases` value with the default, per DSH name rather than per Claude name.** Rejected: the config's own shape is Claude-name-keyed (matching how a maintainer would read and write it next to a `hooks.json`), and a shallow per-Claude-name replace is the same semantics every other object-shaped config field in this bridge already has (`Config` itself has no deep-merge fields). A DSH name gaining or losing an alias is expressed by overriding the Claude name that owns it.

**Validate `toolAliases` through the schemastery `Config` schema (`z.dict(z.array(z.string()))`) instead of a hand-written `validateToolAliases`.** Rejected for now: the coverage suite exercises a "schema bypass" direct `apply()` call (postmortem 0001's namespace-plugin shape guard depends on calling `apply` directly), so the rejection path has to work identically whether the plugin is mounted through `ctx.plugin` or called directly — schemastery's own schema application only runs on the `ctx.plugin` path. `apply()` already validates `stderrSummaryMaxChars` by hand for the same reason; `toolAliases` follows that established shape rather than introducing a second validation path with a different failure mode.

**Push the unsupported-event warning further, e.g. summarizing all skipped events in one line.** Rejected: the bridge already warns per-skipped-hook (one line per non-command hook), and a maintainer scanning logs for a specific missing event benefits more from one distinctly-named line per event than a single aggregate they have to parse.

## Consequences

An unmodified Claude Code `hooks.json` — including izzy's `gate-guard.js` (matcher `Bash|PowerShell`) and `gate-guard-mcp.js` (matched by `tool_name` on the MCP surface) — now fires against this harness's tool calls without rewriting the matcher or the hook script. A hook script that reads `tool_input.command` (the exact field `gate-guard.js` reads) continues to work unchanged, because that field was already name-compatible; only `tool_name` needed the alias layer. `SessionEnd` and `PreCompact` remain unimplemented — this cell's mandate scoped them OUT — but a config wiring either one now gets a load-time warning instead of silence, so the gap is legible rather than a trap. `toolAliases` is additive and backward compatible: a deployment that sets no value gets the exact table above; one already using DSH-native matchers (`bash|pwsh`) keeps working, since the raw DSH name is always a match candidate alongside its aliases.

## Verification

Two new spec files cover the layer directly: `tool-aliases.spec.ts` unit-tests `reverseToolAliases`/`claudeToolName`/`toolMatchCandidates`/`validateToolAliases` and the `parseClaudeCodeConfig` unsupported-event skip against the exact default table (all pure functions, no subprocess); `tool-alias-bridge.spec.ts` drives the REAL agent loop, the REAL bash executor, and REAL hook shell scripts (the existing suite's "prefer the real implementation" rule) to prove a `Bash|PowerShell` matcher denies `bash` and `pwsh` DSH tool calls but not `read`, an `Edit|Write|MultiEdit` matcher denies `edit`/`write`/`str_replace_editor` but not `grep`, a captured `PreToolUse` payload for a `bash` call carries `tool_name: "Bash"` and `tool_input.command` equal to the command text, a captured `PostToolUse` payload carries `tool_name: "Edit"` and `tool_response` with the tool's result text, a configured `toolAliases` override keeps the other defaults working, a malformed `toolAliases` value is rejected at load (`ctx.plugin(...).rejects.toThrow`), and `ConfigChange`/`PreCompact` both produce a named warning. A fix-round-1 addition, `known-events.spec.ts`, closes a Mars-found regression in the same change: the settings-file fallback (`hooksMap = asObject(root.hooks) ?? root`) must not misclassify ordinary settings keys (`model`, `permissions`, `env`) as unsupported hook events while still flagging a real one (`ConfigChange`, `PreCompact`) in that same bare-root shape. `tsc -p packages/hooks/hooks-claude-code` is clean.

`tool-aliases.spec.ts` (10 tests, pure functions, no subprocess) and `known-events.spec.ts` (2 tests, same class) are platform-independent and were run and pass in this session: 10/10 and 2/2. The pre-existing `config.spec.ts` (pure parsing, no subprocess, 12/12) also passes, confirming no regression. `tool-alias-bridge.spec.ts` builds every hook `command` string with node's `path.join` — **not** forward slashes — which on this win32 host produces a backslash path that `bash -c "<command>"` mangles in the command-line argument itself (`command not found`, exit 127); this is a pre-existing, independently-reproduced environmental limitation (the identical failure reproduces against the pre-change source), and exactly why `vitest.config.ts` already excludes `packages/hooks/*` on win32. Run in this session against a throwaway, uncommitted vitest config that lifts that exclusion (never committed), the committed `tool-alias-bridge.spec.ts` measures **6 failed | 4 passed (10)** on this host; every failure traces to the backslash-path mangling (a `deny.sh` command spawned as a mangled Windows path, or a `payload` capture file the mangled script never wrote), not to the alias-bridge matching/payload logic itself, which the passing `tool-aliases.spec.ts` unit tests independently cover. TypeScript and the pure-logic suites are the verified-in-session evidence here; the Linux CI lane (where `packages/hooks/*` is not excluded) is the authority for `tool-alias-bridge.spec.ts` and the pre-existing subprocess-driven suites (`bridge.spec.ts`/`coverage-*.spec.ts`, which show the same class of pre-existing win32 path failures independent of this change — `bridge.spec.ts` alone fails 9/15 on this host, unmodified by this cell).
