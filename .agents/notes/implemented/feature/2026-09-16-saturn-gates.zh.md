# Agent Note: Gates 是工具瀑布流上的一份数据策略，而不是给每个工具写一条分支

Status: implemented

[English](2026-09-16-saturn-gates.md) | 中文

## 问题

harness 此前没有 Gate。它的权限模型是两个全局旋钮——sandbox 文件模式与审批策略的笛卡尔积——而内置的预设表恰好只有三行，其中唯一拥有完整文件访问的那一行（`danger-full-access`）同时把审批设成了 `never`。没有任何地方会去检查一条 shell 命令的文本或一个 MCP 工具的名字，来识别那些本应停下来交给人的动作类别：强制推送、生产部署、读取凭据、付费生成调用、发给真实的人的消息、workspace 之外的 `rm -rf`。唯一真的存在过金钱 Gate 的地方——`packages/saturn/tool-media` 的花费审批——共用的正是同一个全局旋钮，因此在操作者自己的 `defaultPreset: danger-full-access` 之下，它对每一次模型发起的调用都是自动拒绝，而不是去问他。于是摆在面前的选择只有"完整能力但没有 Gate"或"永远说不的 Gate"，而操作者的既定法则是：凭据、金钱、公开行为和不可逆行为永远回到他手上，其余一切照常运行。

## 决策

交付 `@saturnai/dsh-gates`：一个 `tools/pre-execute` 监听器，覆盖在一份"数据"策略之上。六个后果类别（凭据、花钱、发布、对外、身份、破坏性），两种规则形态——MCP 规则匹配工具的名字，因为 MCP 工具的名字本身就说明了它的后果；shell 规则则还要用大小写不敏感的正则匹配命令文本，并且只限定在真正会执行命令行的工具以及真正装着命令行的参数字段上。内置规则点名的是操作者实际挂载的服务器（telegram-hive、shop-ops、gemini-media、saturn-browser、saturndesign，已对照他 `.claude.json` 中的十一个服务器核验），每一条都配了 `mcp__*__…` 通配以覆盖未知服务器上的同种后果。有四条规则是拒绝而非询问——fork bomb、根目录或 home 目录清空、格式化磁盘、直接写入块设备——因为它们不应该能被 session 内部的任何审批买下来；其余一律询问。部署方可以追加规则、按 id 删除某条，或整体替换；无法编译的策略会让插件加载失败，而不是静默地什么都不拦。

有三个组合决策撑起了这个设计。**插件自己从不调用 `ctx.approval`**：它返回 `{ kind: 'ask' }`，由工具注册表去解析，这既让一次调用只对应一个问题，也把"询问/决定"这一对审计事件留在 session 自己的日志里。**被认领的调用就地作答、不再下传**（未被认领的则总是下传），因此把 gates 挂在 Claude Code hook 桥接之前，就意味着 Gate 的类别只被判定一次。**已经自带 `sandbox_permissions` 升级请求的 shell 调用，即便被规则认领也照样下传**，因为 `tool-bash` 会在它自己的函数体里经由同一个审批 seam 解析那次升级——弃权正是让一次 Gate 类的升级调用停在恰好一个问题而不是两个的原因，而且两条路径都不会让未经批准的东西运行：被拒绝、无人可答或没有 agent 的升级会在命令运行之前抛错。`deny` 类别在该检查之前就已判定，所以升级请求永远换不来放行。

插件在询问之前还会读取生效中的审批策略。在 `never` 之下，询问会在任何应答者看到之前就被答成 `rejected`，模型于是会报告一个用户从未做出的拒绝；因此这种情况改为拒绝，并在理由里点名修复方式——把 `permission.defaultPreset` 换成 `full-access-gated`。测试先行：两个测试套件在 `a01573c710` 落地时为 RED（103 个用例，本包源码尚不存在），随后实现落地，未修改任一 spec 文件。

## 曾考虑的替代方案

- **把休眠的 `@deepseek-ai/dsh-hooks-claude-code` 桥接组合进来、指向操作者现有的 `gate-guard.js`，就算完成。** 作为全部答案已否决，作为补充则保留：该桥接对每次调用的每个 hook 都要起一个进程，它的 matcher 是照着 Claude Code 的工具名而非 harness 的工具名写的，而且一份活在仓库之外的个人设置文件里的策略，仓库无法为它写测试。桥接对一切定制行为仍然值得存在；Gate 的这几个类别则是原生、带类型且有覆盖的。
- **在 gate 内部直接调用 `ctx.approval.request()`。** 已否决：注册表本就会带着调用 id、signal 与 session 审计去经由那个 seam 解析一次 `ask`。直接询问会重复那对审计事件，并且在一次会升级的 bash 调用上，为一个动作把两个问题摆到用户面前。
- **对自带 sandbox 升级请求的 Gate 类调用直接拒绝。** 曾作为"保证只有一个问题"的简单办法被考虑，已否决：它保证的是零个问题，并且会教模型去掉升级请求再试一次——对同一条命令来说这是更糟的行为。弃权同时保住了人类决策与问题数量。
- **把这些类别写成每个工具一条分支。** 被仓库自身"不得写无依据的硬编码可调项"的规则否决，也被运维事实否决：挂载一个新的 MCP 服务器是一次策略事件，分支需要改代码并重新构建，而规则只需要一行配置。
- **把文件修改类工具也设门。** 已否决：完整的文件访问正是目的所在。操作者要的是一个能写任何东西、同时金钱、凭据与公开行为仍然会停下来的 session。

## 后果

一个 session 可以拥有完整的文件与 shell 权限，并且在真正要紧的动作上仍然回到人这里，附带一句点名类别、规则以及接下来会发生什么的话。代价严格地只按"被拦下的调用"计：没有系统提示词段落，没有工具 schema，提示词前缀里什么都不加，因此未被认领的调用毫发无损，KV 缓存也绝不会被这份策略弄失效。有三处差距被写进包 README 而不是藏起来：正则读到的是命令怎么写而不是命令会做什么；harness 依然完全没有出网管控；以及无人列出的服务器上的 Gate 类工具，在有规则点名它之前一律通过。本 cell 不拥有的集成项已在它的报告中点名：一行 `full-access-gated` 预设、把本插件挂在 hook 桥接之前的 bundle 行，以及 `tsconfig` 注册——没有那次预设切换，每一次 Gate 类调用都会拒绝而不是询问，而这正是本包能够识别并解释、却无法自行修复的那一种结果。
