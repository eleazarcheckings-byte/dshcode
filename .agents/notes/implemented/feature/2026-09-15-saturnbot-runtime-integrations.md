# Agent Note: SaturnBot .env lane, Telegram/Shopify adapters, deploy hooks, media and model routing

Status: implemented

English | [中文](2026-09-15-saturnbot-runtime-integrations.zh.md)

## Problem

The recon audit of SaturnBot (session 2026-09-15) found a real, durable execution engine that could not yet run a business: credentials could only reach it through an OS environment variable set before the Host launched, `cloud.deploy`/`social.publish`/`creative.generate` were generic operator-webhook stubs with no vendor client, there was no channel to reach izzy's own tools (Telegram, Shopify) at all, every planner/specialist call always used the harness's single configured default provider regardless of tier, and the dashboard wizard had nothing durable to render a first-run or connect-form experience from.

## Decision

A new scoped `.env` loader ([src/adapters/env-file.ts](../../../../packages/saturn/saturnbot/src/adapters/env-file.ts)) reads `<dataDirectory>/.env` once at boot and layers it beneath the inherited process environment (an explicit process variable always wins, matching the harness's own credential-layering convention); the merged environment threads through one shared `toolOptions` object into every adapter and into the engine's own redaction, so `.env`-sourced secrets are treated identically to process-supplied ones everywhere they are checked or redacted.

`integration()`/`deployHook()` in [shared.ts](../../../../packages/saturn/saturnbot/src/adapters/shared.ts) now resolve from a `BotConfig` directly rather than a full tool-dispatch context, so the same resolver serves both a model-dispatched tool call and the engine's own direct report delivery. New adapters in [integrations.ts](../../../../packages/saturn/saturnbot/src/adapters/integrations.ts): `telegram.send` (bot-token-in-URL, not a bearer header, per the Telegram Bot API) posts to a default or supplied chat id; `shopify.orders_list`/`shopify.products_list` read bounded, customer-PII-free commerce data via `X-Shopify-Access-Token`; `shopify.inventory_update` sets one item's quantity after approval. `cloud.deploy` gains a `target` field: `vercel`/`cloudflare-pages` POST straight to the configured deploy-hook URL (credential optional, since the hook URL is itself the secret) after the existing GitHub-publication check, falling back to the prior generic webhook contract unchanged. `creative.generate` checks a duck-typed `options.services?.get('media')` capability first (the C7 `@saturnai/dsh-tool-media` contract) before falling back to its existing webhook.

`LoggedBotModel` ([model.ts](../../../../packages/saturn/saturnbot/src/model.ts)) resolves each call's provider/model/reasoning-effort through a duck-typed `ctx.get('modelRouter')` (the C6 `@saturnai/dsh-model-router` contract) when connected — `coordinator` tier for planning, `specialist` for a role proposal — falling back to the configured `provider`/`model` when no router is connected or it throws/returns an incomplete route; the durable model-request record always reflects the route actually used. `BotSnapshot` gains `firstRun` (current goal/workspace/provider plus known-provider credential presence) and `integrationCatalog` (the static field-level connect-form catalog, each field marked `secret` or not so a UI never echoes a credential value) via new [wizard.ts](../../../../packages/saturn/saturnbot/src/wizard.ts), computed in `SaturnBotService.project()` the same way the existing `connections` projection already was.

## Alternatives considered

Reusing the harness's `dsh-credentials-local` file-backed provider was considered first, since it already layers a project/user `.env` beneath the inherited environment; it was rejected here because its file location is fixed to `$DSH_HOME`/invocation-cwd, not SaturnBot's own `dataDirectory`, and depending on it would add a cross-package dependency for a handful of lines a scoped loader covers directly. Routing `reportChannel: telegram` through a model-visible tool call (reusing `telegram.send`) was rejected in favor of a direct engine-invoked `BotReportDelivery`: a digest send is engine-initiated automation, not a model decision, and forcing it through the approval-gated tool path would either block on an approval nobody is asked for or silently bypass one. A new `ToolEffect` for non-code approval-gated actions (Shopify inventory writes) was considered instead of reusing `'social'`; the existing codebase already overloads `'social'` for `creative.generate` (not literally social), so a new effect would only fragment an already-established convention for "needs approval, no git stage" actions.

## Consequences

Existing 54 saturnbot-package tests plus 21 new ones are green (`node_modules/.bin/vitest run packages/saturn/saturnbot`: 9 files, 75 tests). New mocked-HTTP tests cover the `.env` loader (parsing, precedence, oversized-file rejection), Telegram send and its missing-chat-id rejection, Shopify reads/writes and its missing-resource rejection, both new `cloud.deploy` targets (including an embedded-credential rejection), `creative.generate`'s media-first routing and webhook fallback, and the model router's coordinator/specialist tier resolution with its fallback-on-absence and fallback-on-throw paths. `tsc -p packages/saturn/saturnbot/tsconfig.json --noEmit` is clean.

Known gaps, recorded in the package README's Known Limitations: only Telegram implements a live `reportChannel`; the generic `cloud.deploy` webhook target, `social.publish`, and `creative.generate`'s webhook fallback still need an operator-built middleware; the Telegram/Shopify/Vercel/Cloudflare Pages adapters follow public documentation but were not exercised against a live account this session (the Vercel/Cloudflare deploy-hook response is therefore retained as opaque JSON rather than asserted field-by-field); and `firstRun.credentials`' known-provider table is a curated static list that returns nothing for an unrecognized provider id rather than guessing. `ui-saturnbot` (a sibling cell) codes its wizard against these exact shapes with a local type; integration reconciles any RPC drift.
