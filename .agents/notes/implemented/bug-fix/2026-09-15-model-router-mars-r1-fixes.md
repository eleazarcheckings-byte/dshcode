# Agent Note: model-router — Mars r1 fix (harness availability was a constant, not a probe)

Status: implemented

English | [中文](2026-09-15-model-router-mars-r1-fixes.zh.md)

## Problem

Mars's first review of C6 (`.../scratchpad/review/C6-model-router-providers-r1.md`) returned REVISE. The load-bearing finding (F1): `ModelRouterService.harnessAvailable()` probed only each harness's wrapper package (`@deepseek-ai/dsh-subagent-codex` / `-claude-code`) via `require.resolve`, anchored at `model-router`'s own module. Those two wrapper packages were declared as `optionalDependencies: "workspace:^"` of `model-router` itself, so pnpm linked them into `model-router`'s own `node_modules` on every workspace install — the probe returned `true` unconditionally in this checkout (Mars verified both resolve). The README and both YAML comments asserted the opposite: that each harness "still self-hides when its own package-local platform CLI package is not installed." The unit test covering this (`model-router.spec.ts:103`) asserted `externalHarnessMounted('codex') === harnessAvailable('codex')` — true by construction, so it could never catch a wrapper-resolves-but- CLI-absent false positive. Two secondary findings: no committed `test(saturn):` RED commit exists for this cell (F2, declared as a deviation in the original report, not tamper — no test files existed to tamper with), and the `saturn-model-router` namespace has no `settings.plugin.item` client card so it renders nothing in Settings (F3, correctly diagnosed by the original builder as outside C6's IN list — `packages/client/ui-settings-plugins` is a different cell's scope).

## Decision

- **Two-stage resolution, not a single wrapper probe.** New `harnessCliResolvable(resolver, subagentPackage, cliPackage, createRequireFn)`: (1) resolve the wrapper's own `package.json` from `resolver` (anchored at `model-router`); (2) resolve the wrapper's *actual* CLI dependency — `@openai/codex` for `codex`, `@anthropic-ai/claude-agent-sdk` for `claude-code` (confirmed from `packages/subagent/subagent-codex/package.json` and `packages/subagent/subagent-claude-code/package.json`'s own `dependencies`) — from a `require` anchored at that manifest. Only when both stages succeed does `harnessAvailable()` report true. This is the same resolution order Node itself uses to load a dependency from inside a package, so a wrapper that resolves purely because it sits in some consumer's `devDependencies` graph can no longer masquerade as "CLI installed."
- **Removed the `optionalDependencies` that made the probe a constant.** `model-router/package.json` no longer lists `@deepseek-ai/dsh-subagent-codex` / `-claude-code` as `optionalDependencies` (they remain `devDependencies`, needed for this package's own tests, which are never installed in a production install of the published package).
- **Constructor now takes an injectable second-stage resolver.** `ModelRouterService`'s constructor gained a fourth parameter, `createRequireFn` (defaults to `node:module`'s `createRequire`), alongside the existing `resolver` parameter — both overridable in tests, both real-environment defaults in every actual mount.
- **Replaced the tautological unit assertion's blind spot with deterministic coverage.** New `tests/harness-cli-resolution.spec.ts` injects fake two-stage resolvers to fix the true/false split independently of what happens to be installed in this checkout: wrapper-absent → false, wrapper-present-but-CLI-absent → false (the exact false positive Mars found), both-present → true; plus a `ModelRouterService`-level case proving `externalHarnessMounted('codex')` stays `false` with the toggle **on** when the wrapper resolves but its CLI dependency does not. The existing assertion at `model-router.spec.ts:103` is kept (real-environment resolution is still a valid invariant to hold) with a comment pointing at where the deterministic split now lives.
- **README/README.zh updated** to describe the two-stage check instead of the single-package probe; translation pairing re-recorded.

## Deviations from the fix list (declared, not silent)

- **Did not build the `settings.plugin.item` client card (F3).** Confirmed again this round: `packages/client/ui-settings-plugins` is not in C6's IN list (`SPEC.md` §3 C6); building it here would be scope creep into another cell. Left as an `integration_needs` item, as the original builder already flagged.
- **No separate RED commit exists for the original four test files (F2), and this fix round does not retroactively create one** — there is nothing to make RED-then-green for work already merged; the new behavior added in this round (`harnessCliResolvable` and its false-positive-guarding tests) *was* committed RED first (`test(saturn): RED — two-stage harness CLI resolution for externalHarnessMounted`, confirmed failing 4/5 against the pre-fix code) and implemented after, per SPEC §6.
- **Edited the already-committed test file `tests/harness-cli-resolution.spec.ts` after its RED commit**, before the fix commit — but not to weaken or add assertions. The RED commit's `ModelRouterService`-level cases called `ctx.plugin(ModelRouterService, {}, resolver, createRequireFn)` expecting `ctx.plugin` to forward the extra constructor arguments; `vendor/cordis`'s `Registry.plugin(plugin, config, getOuterStack)` only ever forwards `(ctx, config)` to a class plugin's constructor, so the injected fakes never reached the instance and those two cases exercised the real environment by accident (matching this checkout's real resolution by luck, not by design). Fixed to construct `new ModelRouterService(ctx, {}, resolver, createRequireFn)` directly — `Service`'s own constructor (`vendor/cordis/src/service.ts`) registers the instance on `ctx` via `ctx.reflect.provide` independently of the plugin/fiber machinery, so direct construction is the correct way to inject test doubles here. No assertion's expected value changed; only how the service under test was constructed.
- **Did not touch `packages/bundle/base/cordis.patch.yml`, `packages/bundle/web-app/cordis.patch.yml`, or the `cordis` preset.** The `disabled: !!js ctx.get('modelRouter')?.externalHarnessMounted(...)` expressions in all four rows already delegate entirely to `externalHarnessMounted()`; fixing that service method's internals requires no change to any YAML row, and `bundle-compose.spec.ts`'s YAML-shape assertions (unchanged) still pass.

## Alternatives considered

**Spawn each harness's CLI with `--version` (or similar) instead of a `require.resolve` probe.** Rejected: the disabled-expression evaluator (`interpolate`, a synchronous `!!js` `eval`) cannot await a child process, and a spawn probe would add real latency and a side effect (starting a process) to what is meant to be a cheap, synchronous gate evaluated on every composition load — the same reasoning the original implementation already documented for choosing `require.resolve` over a `PATH` lookup.

**Probe the CLI package directly from `model-router`'s own resolver, skipping the wrapper-manifest indirection** (i.e. just add `@openai/codex` / `@anthropic-ai/claude-agent-sdk` next to the wrapper in one flat resolver call). Rejected: this would report "available" for a CLI package that happens to be reachable from `model-router`'s own module graph for an unrelated reason (a transitive dependency of some other mounted package, say) even when the harness's own wrapper was never installed at all — exactly the kind of environment-dependent false positive this fix is closing. Resolving the CLI *from inside the wrapper's own manifest* ties the check to the one dependency edge that actually matters: does *this* wrapper have *its* CLI.

**Make `harnessCliResolvable` a private method on `ModelRouterService` instead of an exported function.** Rejected: `packageResolvable` was already exported for direct unit testing without going through the service; keeping `harnessCliResolvable` symmetrically exported lets `tests/harness-cli-resolution.spec.ts` test the two-stage resolution logic in isolation from `ModelRouterService`'s settings/context plumbing, the same separation the original test suite already relied on.

## Consequences

**Cost:** `harnessAvailable()` now does two `require.resolve` calls instead of one per harness (still cached per process, so the added cost is at most once per harness per process lifetime). `ModelRouterService`'s constructor grew a fourth parameter; every call site outside tests already used the 2-arg `(ctx, config)` form cordis's plugin machinery supplies, so no production call site changes.

**Bought:** the toggle genuinely cannot surface a tool with nothing behind it. Before this fix, in any environment where the wrapper package happened to be reachable (which, per Mars's own probe, was true in this very checkout via `optionalDependencies`), flipping `externalHarnesses` would have mounted a Host row and preset tool row for a CLI that was never actually installed — the exact failure mode the README and this package's own doc comments claimed was impossible.

## Testing

Confirmed RED first (committed separately, before the fix): 4 of 5 failed against pre-fix code — `harnessCliResolvable is not a function` for three, and the fourth's real-environment fallback returned `true` where the injected-fake-driven expectation was `false`. Fixed the test's own `ModelRouterService` construction (see Deviations), then implemented the two-stage probe; all 5 pass green, and the existing 11 tests in `model-router.spec.ts` and `bundle-compose.spec.ts` still pass unchanged (16/16 for the package).
