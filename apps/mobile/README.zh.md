# Saturn AI 移动配套应用

[English](README.md) | 中文

`@saturnai/mobile-companion` 是一个 Capacitor 壳应用，用于让 iPhone 或 Android 手机与正在运行的 Saturn AI 主机配对（SPEC.md §8：“harness 始终留在本地主机……iOS 和 Android 提供原生配套壳，与用户正在运行的主机配对，并以原生外壳渲染同一份 web UI，外加手机真正擅长的那件事：随时随地批准 SaturnBot 与 agent 的操作、查看整个机群、阅读裁定”）。本应用不运行任何模型；配对完成后，整个屏幕会交给主机自身的 web 应用，这里没有对 web UI 的分叉。

本目录**不是** pnpm 工作区包。它有自己的 `package.json`，使用普通的 `npm` 安装与构建，独立于仓库根目录的 pnpm lockfile —— 详见下文“为什么用 npm 而不是 pnpm”。

## 目录结构

```
apps/mobile/
  src/                  the native-side screens: plain TypeScript + one HTML page + one CSS file
    lib/                pairing, token storage, event mapping, cert-pin comparison — all unit-tested
    screens/            pairing + notification-list DOM controllers
    index.html           the app shell (pairing / lock / offline / notifications / connecting screens)
    styles.css            SPEC.md §2 tokens: bg/surface/ink/accent, the -18° ring mark, the motion system
  assets/
    fonts/              Instrument Sans (variable, OFL) + Commit Mono (MIT), both self-hosted, with license files
    icons/              the 1024×1024 ring-mark icon source
  resources/            @capacitor/assets input (icon.png, icon-foreground.png, icon-background.png, splash.png, splash-dark.png)
  tests/                vitest unit tests for src/lib
  ios/, android/        generated by `npx cap add ios` / `npx cap add android` (committed; native build output is gitignored)
  capacitor.config.ts
  vite.config.ts        bundles src/ -> www/ (Capacitor's webDir)
  vitest.config.ts
```

（`src/` 是原生侧界面：纯 TypeScript + 一个 HTML 页面 + 一个 CSS 文件；`lib/` 是配对、令牌存储、事件映射、证书指纹比对，均有单元测试覆盖；`screens/` 是配对界面与通知列表的 DOM 控制器；`assets/fonts` 为本地托管的 Instrument Sans 与 Commit Mono 并附许可证文件；`resources/` 是 @capacitor/assets 的输入文件；`ios/`、`android/` 由 Capacitor 生成并已提交，原生构建产物已被 gitignore。）

## 配对协议（SPEC.md §8，具约束力）

主机（`packages/saturn/remote-access`，M1 分支）展示一个二维码，编码为：

```json
{ "v": 1, "name": "<host name>", "url": "https://<lan-ip>:<port>", "token": "<opaque>", "fingerprint": "<sha256 hex>", "expires": "<ISO time>" }
```

1. **扫描或粘贴**（`src/screens/pairing.ts`）—— 扫描路径使用 `@capacitor/camera` 拍一张照片，再用 `jsqr` 在本地解码（原因见下文“为什么用 jsQR 而不是条码扫描插件”）；直接粘贴 JSON 是文档化的备用方案，效果完全相同。
2. **解析与校验**（`src/lib/pairing.ts`）—— 版本号、必须为 https、`expires` 必须是合法 ISO 时间，且当 url 为局域网地址（即非 `*.trycloudflare.com`）时必须携带 64 位十六进制 `fingerprint`。隧道模式的载荷可省略指纹，因为 cloudflared 自带 TLS。
3. **交换令牌**（`src/lib/remoteApi.ts` 的 `pairWithHost`）—— 向 `POST <url>/saturn/remote/pair` 发送 `{ token, device }`，并设置 `credentials: 'include'`，让主机的会话 Cookie 落入该 WebView 对应源的 Cookie 存储中。响应 `{ deviceToken, sessionCookieName }` 由 `src/lib/tokenStore.ts` 保存。
4. **打开** —— “打开 Saturn AI”操作会让 WebView 自身的 `window.location` 跳转到配对得到的 `url`；第 3 步写入的 Cookie 为该次加载鉴权，之后应用自身的 API/事件调用则由 `deviceToken` 承载的 Bearer 令牌鉴权。

## 安全模型

- **证书锁定的 HTTPS（局域网模式）。** `src/lib/certPin.ts` 是经过测试的纯 SHA-256 指纹比对逻辑；真正拦截 TLS 握手的部分是原生且平台相关的：
  - **Android**（已实现，随 debug 构建一起编译）：`android/app/src/main/java/ai/saturnai/mobile/PinningWebViewClient.java` 继承 Capacitor 的 `BridgeWebViewClient`，重写 `onReceivedSslError` —— Android 本就只在平台不信任某证书时（正是局域网自签证书这种情况）才调用它，且默认（未重写时）就是拒绝。这里的重写直接从 `@capacitor/preferences` 在 `tokenStore.ts` 写入时所用的同一个 `CapacitorStorage` SharedPreferences 分组中读取配对指纹，只有完全匹配才放行。
  - **iOS**（已写明步骤，本机无法构建，见下文“Mac 上的步骤”）：等价方案是在 `WKNavigationDelegate` 的 `didReceive challenge` 回调中，用 `SecTrustCopyCertificateChain`/`SecCertificateCopyData` 取出证书并与同一枚指纹比对，加入 `ios/App/App/AppDelegate.swift` 或桥接注册的 `WKUIDelegate`。
- **为什么 `capacitor.config.ts` 里 `allowNavigation` 是 `['*']`。** 主机地址（局域网 IP 或 `*.trycloudflare.com` 子域名）只有在配对时才能得知，构建期无法预先写死白名单。这是刻意的、已文档化的取舍，而非疏漏 —— 应用永远只会跳转到用户自己二维码指定的那个精确 `url`，且每次请求仍会经过证书锁定检查（局域网模式）或 cloudflared 自带的 TLS（隧道模式），外加每设备的 Bearer 令牌。详见 `capacitor.config.ts` 顶部注释。
- **恢复前台时的生物识别/密码锁**（`src/lib/lock.ts`，`@aparajita/capacitor-biometric-auth`）—— `allowDeviceCredential: true` 意味着即使手机未录入生物特征，也会弹出 PIN / 图案 / 密码提示，而不是完全不设锁。
- **撤销配对** —— `DELETE <url>/saturn/remote/devices/<id>`（`src/lib/remoteApi.ts` 的 `revokeDevice`）与离线界面的“忘记此主机”都会立即清除本地会话。

## 通知

`src/lib/eventsMapper.ts` 把 `GET <url>/saturn/remote/events` 的事件载荷（`{ type, title, body, sessionId?, id, at }`）映射为本地通知描述，沿用主机自身裁定卡片的措辞：“需要批准”（approval 且主机未给标题时）、“裁定 PASS/REVISE/REJECT”（从 verdict 事件的正文或标题解析得出）、“SaturnBot 需要你”（saturnbot 且主机未给标题时）。`src/lib/remoteApi.ts` 的 `RemoteEventsClient` 在前台时用 `EventSource` 打开该事件流（走 Cookie 鉴权，因为 `EventSource` 无法设置 `Authorization` 头），并额外提供一个用 Bearer 令牌鉴权的 `pollOnce()` 供后台轮询调用。`src/notificationLog.ts` 在本地保留最近 100 条，供应用内“动态”列表展示，其样式正是 SPEC.md §2 在产品各处反复出现的那张裁定卡片。

### iOS —— Mac 上的步骤（本机无法运行）

`npx cap add ios` 已经用 **Swift Package Manager** 生成了 `ios/App`，而非 CocoaPods —— 这里没有 `Podfile`，**不需要**执行 `pod install`。在装有 Xcode 的 Mac 上：

```sh
cd apps/mobile
npm install
npm run build && npx cap sync ios
open ios/App/App.xcodeproj      # or: npx cap open ios
```

1. Xcode 打开工程时会自动解析 Swift Package 依赖（`ios/App/CapApp-SPM/Package.swift`），无需额外操作。
2. 选择 **App** scheme 与某个模拟器或真机，Product → Run，先验证配对/锁屏/离线三个界面，再着手签名。
3. **签名**：项目设置 → Signing & Capabilities → 选择你的 Team；使用个人 Apple ID 时 Xcode 会自动管理开发证书。即便只是真机调试，这一步也是必需的，早于 TestFlight。
4. **证书锁定**（见上文“安全模型”）：添加一个 `WKNavigationDelegate`，在 `didReceive challenge` 中拦截 `NSURLAuthenticationMethodServerTrust`，取出叶证书的 DER 字节（`SecCertificateCopyData`）、做 SHA-256，与 Android 端 `PinningWebViewClient` 读取的同一枚指纹比对（从 `UserDefaults` 的 `CapacitorStorage` group 中取 —— 这是 `@capacitor/preferences` 在 iOS 上的存储位置 —— 键名 `saturn.remote.session`，取其中的 `fingerprint` 字段）。将其接入 `ios/App/App/AppDelegate.swift` 或 Capacitor 桥接视图控制器上的 `WKUIDelegate`。
5. **Background Modes 能力**（见下文“后台事件投递”）：Signing & Capabilities → **+ Capability** → **Background Modes** → 勾选 **Background fetch** 与 **Background processing**。`Info.plist` 的 `BGTaskSchedulerPermittedIdentifiers` 与 `AppDelegate.swift` 中的 `BackgroundRunnerPlugin` 调用已经提交；这个勾选框是唯一必须由 Xcode 写入 `.pbxproj` 的部分。
6. **TestFlight**：这正是 SPEC.md §8 点名的资金关卡（Gate）—— 需要先有 Apple 开发者计划会员资格（每年 99 美元），Xcode 才能创建 App Store Connect 记录。在做出这个决定之前，以上所有步骤都无需付费会员资格。做出决定后：Product → Archive，通过 App Store Connect 分发，再到 App Store Connect → TestFlight 中添加构建版本与测试人员。

## 为什么用 npm 而不是 pnpm

仓库根目录的 `pnpm-workspace.yaml` 与根 `package.json` 的 npm `workspaces` 数组都已经匹配了 `apps/*` 这个通配符，因此 `apps/` 下的**任何**目录 —— 包括本目录 —— 一旦存在，就会隐式成为 pnpm 工作区成员，完全不需要再对任何一个文件做修改。这对一个理应只用 npm 的目录来说是真实的风险：本次会话曾多次观察到 `apps/mobile/node_modules` 中特定包的内容（`@capacitor/android`、`@aparajita/capacitor-biometric-auth`）在构建步骤之间消失，这与“仓库中别处正在执行一次根级 `pnpm install`，通过既有通配符发现了这个新的工作区成员，并按一份根本没有它条目的 pnpm lockfile 去调和其 `node_modules`”这一情形完全吻合。具体的修复建议见本分支报告中的 `integration_needs`（把 `apps/mobile` 从这两处通配符中排除，或单独加一条忽略规则）—— **不要**为了“正式收编”它而在 `pnpm-workspace.yaml` 里再加一行 `apps/mobile`；需要的修复方向恰恰相反。

对本地构建者的实际影响：请在普通 shell 里执行 `npm install`，并且在依赖 `apps/mobile/node_modules` 完整无损的前提下，避免同时执行根级 `pnpm install`；如果已经执行过，构建前先 `rm -rf node_modules && npm install` 重装一遍。

## 为什么用 jsQR 而不是条码扫描插件

`@capacitor-community/barcode-scanner`（`@capacitor-community` 作用域下唯一对应的插件）的 peerDependency 是 `@capacitor/core@^5`，与本应用所用的 `@capacitor/core@^8` 技术栈不兼容。SPEC.md §8 要求的是“摄像头（或条码扫描器）”—— 括号内给出了另一种选择的余地 —— 因此配对界面使用官方的 `@capacitor/camera` 拍一张照片，再用 `jsqr`（MIT 协议，零原生依赖）在本地解码，而不是为了迁就一个未跟进维护的插件而把整套 Capacitor 技术栈降级。

## 后台事件投递

iOS 与 Android 都不会在应用进入后台后继续保持 `EventSource` 连接，因此由 `@capacitor/background-runner`（官方 `@capacitor` 作用域）安排一个独立于 WebView、自行运行的周期性轮询：

- **`assets/background-runner.js`** 是一个**生成文件**（`scripts/backgroundRunnerBuild.mjs`，通过 `npm run build:background-runner` 运行，并作为本包的 `prebuild` 挂接）—— 它把 `src/lib/backgroundEventsCore.js` 里的纯逻辑辅助函数（SSE 帧解析、事件 id 的数值排序、事件到通知的映射）内联到 `scripts/background-runner.entry.js` 的 OS 定时任务接线代码之下，因为该插件的隔离 JS 引擎完全没有模块加载器，根本无法执行 `import`/`export` 语句。如果提交的文件与一次全新渲染结果出现漂移，`tests/backgroundRunnerGenerated.test.ts` 会让 `npm test` 失败 —— 这样两份源文件就不会像手工镜像那样悄悄产生分歧。
- **每一次触发时**，运行器会在 `GET /saturn/remote/events` 请求上带上 `Last-Event-ID` 请求头（而不是 `?since=` 查询参数 —— 主机的路由会剥离查询字符串、始终路由到它的 SSE 流，所以基于查询参数的轮询永远不会结束：见下文“本轮已修复”），并以 8 秒的读取截止时间增量读取响应体，超时后主动取消 reader，让连接真正关闭，而不是一直挂到操作系统把整个任务杀掉。事件 id（`String(sequence)`，一个普通递增计数器）按**数值**比较；每条触发的通知都携带 `extra: { deepLink, eventId, type }`——与前台路径 `src/lib/eventsMapper.ts` 附加的结构完全一致——因此点击能正确跳转；`src/main.ts` 的 `onNotificationTapped` 处理函数会对完全没有 `extra` 的通知（例如旧版本触发的，或系统自身的通知）做出防护。
- **`src/lib/backgroundSync.ts`** 是应用侧的另一半：在配对成功后、撤销/忘记主机时、以及每次启动时，通过 `dispatchEvent('storeSession', …)` 把已配对的会话推送进这个隔离的 KV 存储 —— 该运行环境看不到 `@capacitor/preferences`。
- **`capacitor.config.ts`** 的 `plugins.BackgroundRunner` 配置块（`buildBackgroundRunnerConfig()`）注册了一个每 15 分钟重复一次的轮询（这是 Android 对重复后台任务的下限；iOS 的 BGTaskScheduler 只把这个数字当作提示，实际节奏由系统自行决定）。
- **Android**：已完整接入，且是下面 debug 构建的一部分 —— `android/app/build.gradle` 的 `flatDir` 条目与 Gradle 插件模块均已就位；APK 一侧不需要额外代码。
- **iOS**：`Info.plist` 的 `BGTaskSchedulerPermittedIdentifiers`/`UIBackgroundModes` 与 `AppDelegate.swift` 中的两处 `BackgroundRunnerPlugin` 调用均已提交，但 **Background Modes 能力**（Background fetch + Background processing）仍需在 Xcode 的 Signing & Capabilities 标签页中手动打开 —— 这一步是仅限 Mac、修改 Xcode 工程文件的操作，没有可用纯文本编辑替代的办法。见下文“Mac 上的步骤”。
- **无论哪个平台**：真正“锁屏也能立即收到推送”（完全没有轮询延迟）都需要主机通过 APNs/FCM 推送，这仍然超出本分支范围，与此前一致。

**本轮已修复（Mars r2，`M3-apps-mobile-r2.md`）：** 此前版本的运行器调用的是 `fetch('…/events?since=poll').then(r => r.text())`——主机的这条路由只支持 SSE、从不自行关闭（`packages/saturn/remote-access/src/proxy.ts` 的 `stream()`，只有 25 秒一次的心跳、没有结束），所以这次调用永远不会 resolve，后台通知也就永远不可能触发。它还把事件 id 当字符串比较（`"10" <= "9"` 为真，一旦超过个位数就会悄悄丢弃 10 到 89 之间的所有事件），并且触发的通知不带 `extra`，导致在 `main.ts` 里点击时崩溃。以上三点均已在上文修复；鉴于隔离引擎文档化的 Web API 范围（`fetch`、`TextDecoder`、定时器 —— 没有 `AbortController`），这里的读取截止时间方案是尽力而为的折中，尚未在真机或模拟器上以真实的 OS 定时任务跑过一遍 —— `npm test` 验证的是纯逻辑（帧解析、id 排序、`extra` 的结构），而不是端到端的真实网络/系统行为。

## 已知限制与遗留工作

- **iOS 未在本机构建。** Xcode 工程、其 Swift Package 依赖、证书锁定用的 `WKNavigationDelegate`，以及上面提到的 Background Modes 能力开关，均已写明步骤，但均未在真机/模拟器上验证，详见“Mac 上的步骤”。
- **Android debug APK 未签名**（使用 Gradle 自动生成的 debug 密钥库）—— 侧载安装是预期用法，尚不适用于 Play 管理中心上架。
- **没有针对 §2 样式的视觉回归测试**（圆环标记、裁定卡片配色）——`npm test` 覆盖的是配对/令牌/通知的*逻辑*，不覆盖像素级输出。
