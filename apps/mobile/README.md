# Saturn AI mobile companion

English | [中文](README.zh.md)

`@saturnai/mobile-companion` is the Capacitor shell that pairs an iPhone or Android phone with a running Saturn AI host (SPEC.md §8: "the harness stays a local host … iOS and Android ship a native companion shell that pairs with the user's running host and renders the same web UI with native chrome, plus the one thing a phone is for: approving SaturnBot and agent actions, watching the fleet, and reading verdicts from anywhere"). It does not run a model, and nothing here is a fork of the web UI — once paired, the app hands the whole screen to the host's own web app.

This directory is **not** a pnpm workspace package. It has its own `package.json` and is installed and built with plain `npm`, independent of the repo's root pnpm lockfile — see "Why npm, not pnpm" below.

## The pairing contract (SPEC.md §8, binding)

The host (`packages/saturn/remote-access`, cell M1) shows a QR code encoding:

```json
{ "v": 1, "name": "<host name>", "url": "https://<lan-ip>:<port>", "token": "<opaque>", "fingerprint": "<sha256 hex>", "expires": "<ISO time>" }
```

1. **Scan or paste** (`src/screens/pairing.ts`) — the camera path uses `@capacitor/camera` to take one photo and decodes it locally with `jsqr` (see "Why jsQR, not a barcode-scanner plugin" below); pasting the raw JSON is the documented fallback and works identically.
2. **Parse and validate** (`src/lib/pairing.ts`) — version, https-only, a well-formed ISO `expires`, and (for a LAN url, i.e. anything that isn't `*.trycloudflare.com`) a 64-hex-char `fingerprint`. A tunnel-mode payload may omit it; cloudflared's own TLS covers that path.
3. **Exchange** (`src/lib/remoteApi.ts`, `pairWithHost`) — `POST <url>/saturn/remote/pair` with `{ token, device }`, `credentials: 'include'` so the host's session cookie lands in the WebView's cookie jar for that origin. The response `{ deviceToken, sessionCookieName }` is stored via `src/lib/tokenStore.ts`.
4. **Open** — the "Open Saturn AI" action navigates the WebView's own `window.location` to the paired `url`; the cookie from step 3 authenticates that load, and the bearer `deviceToken` authenticates the app's own API/event calls afterward.

## Security model

- **Pinned-cert HTTPS (LAN mode).** `src/lib/certPin.ts` is the pure, tested SHA-256 fingerprint comparator. The actual TLS interception is native and per-platform:
  - **Android** (implemented, compiles as part of the debug build): `android/app/src/main/java/ai/saturnai/mobile/PinningWebViewClient.java` extends Capacitor's `BridgeWebViewClient` and overrides `onReceivedSslError` — Android already calls that only for a cert the platform doesn't trust (the self-signed LAN case), and the default when unoverridden is to reject. This override reads the pinned fingerprint straight out of the same `CapacitorStorage` SharedPreferences group `@capacitor/preferences` writes to from `tokenStore.ts`, and proceeds only on an exact match.
  - **iOS** (documented, not built here — see "Mac steps" below): the equivalent is a `WKNavigationDelegate`'s `didReceive challenge` handler evaluating `SecTrustCopyCertificateChain`/`SecCertificateCopyData` against the same pinned fingerprint, added to `ios/App/App/AppDelegate.swift` or a bridge-registered `WKUIDelegate`.
- **Why `allowNavigation: ['*']` in `capacitor.config.ts`.** The host's address (a LAN IP or a `*.trycloudflare.com` subdomain) is only known at pairing time, not at build time, so a fixed navigation allowlist isn't possible. This is a deliberate, documented tradeoff, not an oversight — the app never navigates anywhere except the exact `url` the user's own QR named, and every request to it still carries the pinned-cert check (LAN) or cloudflared's TLS (tunnel) plus the per-device bearer token. See the comment at the top of `capacitor.config.ts`.
- **Biometric/passcode lock on resume** (`src/lib/lock.ts`, `@aparajita/capacitor-biometric-auth`) — `allowDeviceCredential: true` means a phone with no biometry enrolled still gets a PIN/pattern/password prompt rather than no lock at all.
- **Revocation** — `DELETE <url>/saturn/remote/devices/<id>` (`src/lib/remoteApi.ts`, `revokeDevice`) and the offline screen's "Forget this host" both clear the local session immediately.

## Notifications

`src/lib/eventsMapper.ts` maps a `GET <url>/saturn/remote/events` payload (`{ type, title, body, sessionId?, id, at }`) to a local-notification descriptor, keeping the host's own verdict-card language: "Approval needed" (approval, no host title), "Verdict PASS/REVISE/REJECT" (parsed from a verdict event's body or title), "SaturnBot needs you" (saturnbot, no host title). `src/lib/remoteApi.ts`'s `RemoteEventsClient` opens that stream with `EventSource` (cookie-authenticated, since `EventSource` cannot set an `Authorization` header) while the app is foregrounded — and only then: the backgrounded path is the separate runner under "Background event delivery" below, not a method on this client. Its former `pollOnce()` did a one-shot `fetch` + `text()` of that never-closing SSE route (the same never-resolving read Mars r2 found in the runner) and, since nothing called it, was removed rather than fixed. `src/notificationLog.ts` keeps the last 100 locally for the in-app "Activity" list, styled as the same verdict card SPEC.md §2 describes everywhere else in the product.

### iOS — Mac steps (cannot run on this machine)

`npx cap add ios` already generated `ios/App` using **Swift Package Manager**, not CocoaPods — there is no `Podfile` and `pod install` is **not needed**. On a Mac with Xcode installed:

```sh
cd apps/mobile
npm install
npm run build && npx cap sync ios
open ios/App/App.xcodeproj      # or: npx cap open ios
```

1. Xcode resolves the Swift Package dependencies (`ios/App/CapApp-SPM/Package.swift`) automatically on open — no extra step.
2. Select the **App** scheme and a Simulator or a physical device, then Product → Run to sanity-check the pairing/lock/offline screens before wiring signing.
3. **Signing**: Project settings → Signing & Capabilities → pick your Team; Xcode manages a development certificate automatically for a personal Apple ID. A physical-device build needs this even before TestFlight.
4. **Certificate pinning** (see "Security model" above): add a `WKNavigationDelegate` that intercepts `didReceive challenge` for `NSURLAuthenticationMethodServerTrust`, extracts the leaf certificate's DER bytes (`SecCertificateCopyData`), SHA-256-hashes them, and compares against the same pinned fingerprint the Android `PinningWebViewClient` reads (fetch it from `UserDefaults` under the `CapacitorStorage` suite — `@capacitor/preferences`'s iOS storage — key `saturn.remote.session`, field `fingerprint`). Wire it in `ios/App/App/AppDelegate.swift` or via `WKUIDelegate` on the Capacitor bridge view controller.
5. **Background Modes capability** (see "Background event delivery" above): Signing & Capabilities → **+ Capability** → **Background Modes** → check **Background fetch** and **Background processing**. `Info.plist`'s `BGTaskSchedulerPermittedIdentifiers` and `AppDelegate.swift`'s `BackgroundRunnerPlugin` calls are already committed; this checkbox is the one piece Xcode itself has to write into the `.pbxproj`.
6. **TestFlight**: izzy's Apple Developer Program membership ($99/yr) is already paid as of 2026-09-15 — this step costs nothing new. On a Mac: Product → Archive, distribute via App Store Connect, then add build/testers in App Store Connect → TestFlight. Nothing above this line needs the paid membership.

## Why npm, not pnpm

Root `pnpm-workspace.yaml` and root `package.json`'s npm `workspaces` array both already glob `apps/*`, so **any** directory under `apps/` — this one included — is implicitly a pnpm workspace member the moment it exists, with no edit needed to either file. That's a real hazard for a directory meant to be npm-only: this session repeatedly observed `apps/mobile/node_modules` losing specific packages' contents (`@capacitor/android`, `@aparajita/capacitor-biometric-auth`) between build steps, consistent with something elsewhere in the monorepo running a root-level `pnpm install`, discovering this new workspace member via the existing glob, and reconciling its `node_modules` against a pnpm lockfile that has no entry for it. See `integration_needs` in this cell's report for the fix this implies (excluding `apps/mobile` from both globs, or giving it a dedicated ignore entry) — **do not** add an explicit `apps/mobile` line to `pnpm-workspace.yaml` to "opt it in" further; the fix is the opposite.

Practical effect for anyone building this locally: run `npm install` from a plain shell and don't run a root-level `pnpm install` while depending on `apps/mobile/node_modules` being intact — or reinstall it (`rm -rf node_modules && npm install`) immediately before a build if you have.

## Why jsQR, not a barcode-scanner plugin

`@capacitor-community/barcode-scanner` (the one plugin in the `@capacitor-community` scope for this) peer-depends on `@capacitor/core@^5`, and is incompatible with the `@capacitor/core@^8` stack this app uses. SPEC.md §8 asks for "camera (or barcode scanner)" — the parenthetical permits either — so the pairing screen uses the official `@capacitor/camera` to take one photo and decodes it locally with `jsqr` (MIT, zero native dependencies) rather than downgrading the whole Capacitor stack to match an unmaintained plugin's peer range.

## Background event delivery

Neither iOS nor Android keeps an `EventSource` connection alive once the app is backgrounded, so `@capacitor/background-runner` (official `@capacitor` scope) schedules a periodic tick that polls on its own, independent of the WebView. **The tick is a bounded poll, not a stream read** — see "Why not the SSE stream" below for why that is a correctness requirement on iOS, not a style choice.

- **`assets/background-runner.js`** is a **generated file** (`scripts/backgroundRunnerBuild.mjs`, run via `npm run build:background-runner` and wired as this package's `prebuild`) — it inlines `src/lib/backgroundEventsCore.js`'s pure helpers (the replay response's JSON shape, numeric event-id ordering, event → notification mapping) beneath `scripts/background-runner.entry.js`'s OS-tick wiring, because the plugin's isolated JS engine has no module loader at all and cannot execute an `import`/`export` statement. `tests/backgroundRunnerGenerated.test.ts` fails `npm test` if the committed file ever drifts from a fresh render, so the two sources can't silently disagree the way a hand-mirrored copy could.
- **On each tick**, the runner calls the host's bounded replay endpoint, `GET /saturn/remote/events/replay?after=<lastSeen>&limit=100` (SPEC.md §8's replay contract — the same event objects the SSE stream carries, but as one `{ events, newest, truncated, gap? }` JSON object a single `response.json()` reads in full, with no held-open connection and nothing read from `response.body`), passing the device's bearer token the same as any other API call. `after` starts at `0` on first ever run and otherwise at the id persisted from the previous tick. When the response reports `truncated: true` (more events were available than `limit`), the tick fetches up to 4 more pages in the same run, advancing `after` each time, so a large backlog doesn't take multiple 15-minute ticks to drain. When it reports `gap: true` (the requested `after` was older than the host's ring buffer retains), the page still starts at the oldest event the host kept and is processed exactly like any other page — some events between the last successful tick and this one are unrecoverably gone, but the cursor still advances correctly from what the host reports next. Event ids (`String(sequence)`, a plain counter) are compared **numerically** throughout (`compareEventIds`/`resolveReplayCursor`), and each fired notification carries `extra: { deepLink, eventId, type }` — the same shape `src/lib/eventsMapper.ts` attaches on the foregrounded path — so a tap deep-links correctly; `src/main.ts`'s `onNotificationTapped` handler guards against a notification with no `extra` at all (an older build's, or a stray OS one).
- **`src/lib/backgroundSync.ts`** is the app-side half: it pushes the paired session into the runner's isolated `CapacitorKV` store via `dispatchEvent('storeSession', …)` after pairing, on revoke/forget, and once at boot — the runner's context can't see `@capacitor/preferences`.
- **`capacitor.config.ts`**'s `plugins.BackgroundRunner` block (`buildBackgroundRunnerConfig()`) registers a repeating tick every 15 minutes (Android's own floor for a repeating background task; iOS's BGTaskScheduler treats the number as a hint and decides the actual cadence itself — the OS, not this app, ultimately controls when a tick actually runs).
- **Android**: fully wired and part of the debug build below — `android/app/build.gradle`'s `flatDir` entry and the Gradle plugin modules are already in place; no APK-side app code needed. The plugin's Android engine ships as a prebuilt native `.aar` with no source in this checkout, so the replay poll's live behavior there is inferred from the plugin's documented JS API surface (`fetch`, `console`, timers, `CapacitorKV`/`CapacitorNotifications`), not read from source the way the iOS finding below was.
- **iOS**: `Info.plist`'s `BGTaskSchedulerPermittedIdentifiers`/`UIBackgroundModes` and `AppDelegate.swift`'s two `BackgroundRunnerPlugin` calls are already committed, but the **Background Modes capability** (Background fetch + Background processing) still has to be turned on in Xcode's Signing & Capabilities tab — that one step is a Mac-only, Xcode-project-file change with no text-editable equivalent. See "iOS — Mac steps" below.
- **Either platform**: true push-while-locked delivery (no periodic-tick delay at all) would need the host to push through APNs/FCM — out of this cell's scope, same as before.

### Why not the SSE stream

The previous revision of this runner read the host's held-open `GET /saturn/remote/events` stream directly, with a `Last-Event-ID` header and an 8-second read deadline that canceled the reader on expiry. **That is non-functional on iOS with the currently pinned plugin version**, not merely unverified — the plugin's own shipped Swift source proves it:

- `node_modules/@capacitor/background-runner/ios/Sources/RunnerEngine/JSResponse.swift` — the isolate's `Response` object (`JSResponseExports`) exposes only `ok`, `status`, `url`, `text()`, and `json()`. There is no `body` property and no `ReadableStream` at all.
- `node_modules/@capacitor/background-runner/ios/Sources/RunnerEngine/JSFetch.swift` — `fetch()` is implemented on `URLSession.dataTask`, and the JS promise it returns resolves **inside the completion handler**, i.e. only once the entire response body has already been buffered by `URLSession`.

Put together: `await fetch(hostUrl + '/saturn/remote/events')` against a stream the host holds open and never closes on its own (a 25-second heartbeat, no end — `packages/saturn/remote-access/src/proxy.ts`'s `stream()`) never resolves on iOS, full stop. The read-deadline logic that was meant to bound the read never even starts, because it was created *after* the `await fetch(...)` line — the same class of hang Mars r2 (`M3-apps-mobile-r2.md`) flagged for the earlier `?since=poll` + `response.text()` version, just relocated one call deeper. This was found reading the plugin's committed source, with no device or emulator involved. The bounded replay endpoint above (`response.json()` against a request that always completes, never a stream the host holds open) has no equivalent failure mode on either platform, because nothing in the path ever depends on `response.body`.

**Fixed across rounds (Mars r2 `M3-apps-mobile-r2.md`, Mars r3 `M3-apps-mobile-r3.md`):** r1 called `fetch('…/events?since=poll').then(r => r.text())` against the SSE-only route, which never resolved. r2 replaced that with the `Last-Event-ID` + streaming-read approach described above, which fixed the *host's* route selection but depended on a stream read that r3 proved unreachable on iOS. Both are now gone: the tick reads the bounded `/events/replay` endpoint with `response.json()` and nothing else. String-vs-numeric id comparison (`"10" <= "9"` silently dropping ids 10–89) and the missing notification `extra` were fixed in r2 and remain fixed. `npm test` verifies the pure logic end to end — the replay response's JSON shape, numeric id ordering, gap and truncated-paging handling, and the notification `extra` shape — but the live network/OS behavior (an actual OS-scheduled tick firing a real notification) has still not been exercised on a physical device or emulator; that remains true for any background-runner tick, on any host contract, until one is.

## Known Limitations and Deferred Work

- **iOS is not built on this machine.** The Xcode project, its Swift Package dependencies, the certificate-pinning `WKNavigationDelegate`, and the Background Modes capability toggle above are all documented but unverified on-device; see the Mac steps.
- **The Android debug APK is unsigned** (Gradle's auto-generated debug keystore) — expected for sideloading, not suitable for Play Console.
- **No visual regression coverage** for the §2 styling (ring mark, verdict-card colors) — `npm test` covers the pairing/token/notification *logic*, not pixel output.
